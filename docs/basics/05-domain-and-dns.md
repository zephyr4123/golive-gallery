# 05 · 域名与 DNS

> 你花钱买了个域名,填了几行表格,然后等。有时候十分钟就好了,有时候半天不生效,你不知道该继续等还是哪里配错了。
> 这一篇讲清楚域名到底是什么、DNS 那张表怎么读、以及**「改完要等」到底在等什么**。
>
> 每个概念配一条自查命令——概念记不住没关系,命令能跑出真相。

## 一个域名是怎么组成的

```
denta . golive-gallery . art
  │           │           │
 子域        二级域      顶级域(TLD)
```

**从右往左读**,越往右管得越宽:

- **顶级域(TLD)** —— `.com` `.art` `.cn` `.io` 这些,由各自的**注册局**管理
- **二级域** —— 你花钱买到的那一段,买的就是"在某个 TLD 下占住这个名字"
- **子域** —— 买到二级域之后,**你想开多少个子域就开多少个,全部免费、随时增删**

最后这条很多人不知道,却是本项目的基础:一个域名可以挂无数个站。本项目三个示范站 `dreamcore`、`acreage`、`denta` 全在同一个域名下,只买了一次。

## 模型一:域名 = 一条登记记录,注册商 ≠ 解析商

买域名买到的不是一台服务器,而是在**注册局**登记的一条记录:"这个名字归你,并且由某几台 DNS 服务器负责解析它"。

两个角色经常被混为一谈,其实完全可以分开:

- **注册商**(registrar):你在哪买的域名、在哪续费——本项目在腾讯云
- **DNS 托管商**(解析商):谁来回答"这个域名指向哪"——本项目在 Cloudflare

买域名时注册商默认把解析也包了(腾讯云配 DNSPod),但你随时可以**只换解析商、不动注册商**——这正是本项目做的事(原因见 [Cloudflare 解析篇](../guide/01-free-hosting/custom-domain-cloudflare.md))。

```bash
whois <你的域名> | grep -iE 'registrar|name server'   # 一条命令看清两个角色
```

⚠️ **域名是租的,不是买断的。** 到期不续费就会被别人抢走,连带你的网站和邮箱一起失效。**开自动续费**,这是最廉价的保险。

## 模型二:DNS 是一张表,每行一条记录

解析商手里是一张表,每行一条记录,回答"这个名字指向什么"。

| 类型 | 含义 | 例子 |
|---|---|---|
| **A** | 名字 → IPv4 地址 | `@ → 185.199.108.153` |
| **AAAA** | 名字 → IPv6 地址 | `@ → 2606:4700::6815:5c13` |
| **CNAME** | 名字 → **另一个名字**(别名) | `dreamcore → <用户名>.github.io` |
| **NS** | 这个域名归谁解析 | `→ buck.ns.cloudflare.com` |
| **TXT** | 一段纯文本 | 平台验证域名归属、邮件反垃圾配置 |
| **MX** | 这个域名的邮件送到哪 | 配企业邮箱时用 |

日常绑网站只会用到 A 和 CNAME 两种,别被这张表吓到。

### CNAME 只能指域名,不能带路径

**这是每个人第一次绑域名都会卡住的地方。**

不存在 `xxx.github.io/仓库名` 这种记录——DNS 层只认识**名字**,不认识 URL,不认识路径。

那平台怎么知道该回哪个站?靠 HTTP 请求里的 `Host` 头(见 [01 篇](01-how-the-web-works.md)):流量到达平台后,平台查"哪个站登记了这个域名",按名字分发。

所以同一个用户的一百个项目站,CNAME 记录值**全都一样**,互不打架。

```bash
dig +short CNAME dreamcore.<你的域名>    # 看别名指向谁
dig +short dreamcore.<你的域名>          # 看最终解析成什么 IP
```

⚠️ 一个常见困惑:在 Cloudflare 里加了 CNAME,`dig` 查出来却是个 IP、看不到 CNAME。这不是配错了——开了橙云代理之后,Cloudflare 会把真实指向藏起来,对外只给自己的边缘 IP。详见 [07 篇](07-cloudflare.md)。

## 模型三:NS 记录 = 这个域名归谁解析

注册局层面记着一条 **NS**(Name Server)记录:这个域名的一切解析问题,去问这几台服务器。

**换解析商 = 改这条 NS 记录。** 操作入口在**注册商的域名管理页**,不在解析记录页——两者的区别是"由谁解析" vs "解析成什么"。这两个页面长得像,但改错地方不会有任何效果,是新手最常见的原地打转。

查询是一条链,每一环都可能有缓存:

```bash
dig +short NS art. | head -1                       # ① 顶级域的权威服务器是谁
dig +short NS <你的域名> @a.nic.art                 # ② 问注册局:归谁解析(最权威,无缓存)
dig +short NS <你的域名> @8.8.8.8                   # ③ 问公共解析器(有缓存,可能滞后)
```

②和③不一致时,说明 NS 变更已在注册局生效、公共缓存还没过期——**这不是故障,是时间问题**。

## 一次查询实际走了几步

你在浏览器敲下网址,后面这条链子跑了一遍:

```
浏览器  →  操作系统缓存  →  你的解析器(通常是运营商的,或者 8.8.8.8 / 1.1.1.1)
                                      ↓ 如果它也不知道
                              根服务器:".art 归谁管?"
                                      ↓
                              .art 注册局:"这个域名归 buck.ns.cloudflare.com 管"
                                      ↓
                              Cloudflare:"denta 指向 172.67.184.251"
                                      ↓
                              一路缓存着回传给你
```

**这条链上每一环都会缓存结果**,这是 DNS 快的原因,也是"改完要等"的原因。

## 「改完要等」到底在等什么

分两件事,别混:

### 一、新加一条记录

如果这个名字**以前从来没查过**,那么理论上一改就生效——没有旧值可缓存。

⚠️ **但实测不一定这么干脆。** 本项目 2026-08-23 在 Cloudflare 面板里加一条新的 CNAME,直接问 Cloudflare 自己的权威服务器,**约 2.5 分钟才全量收敛**。收敛期间出现过一个很吓人的现象:同一台权威服务器,查小写 `denta` 返回不存在,查 `Denta` 却正常返回——两个应答里的 zone 版本号不同,说明 Cloudflare 边缘的新旧配置并存。

**这不是你配错了,等就行。** 知道有这回事,能省掉一轮"是不是名字打错了"的自我怀疑。

### 二、改一条已经存在的记录

这才是真正要等的情况。每条 DNS 记录都带一个 **TTL**(Time To Live),单位是秒,意思是"拿到这个答案后可以缓存多久"。

- TTL 3600 = 各级缓存最长可能拿着旧值一小时
- TTL 300 = 最多五分钟
- Cloudflare 上写 `Auto` 通常是 300 秒

所以**计划要改记录时,提前几小时把 TTL 调小**,改完再调回去,能大幅缩短等待。

```bash
dig <你的域名> | grep -A1 'ANSWER SECTION'    # 答案前面那个数字就是剩余 TTL 秒数
```

## 排查:一层一层往上问

解析出问题时,**从最权威的一层往下问**,第一个给出正确答案的那层之上都是好的,之下都是缓存没过期。

```bash
# ① 问权威服务器(不经过任何缓存,这是真相)
dig +short <子域>.<你的域名> @$(dig +short NS <你的域名> | head -1)

# ② 问公共解析器
dig +short <子域>.<你的域名> @1.1.1.1
dig +short <子域>.<你的域名> @8.8.8.8
dig +short <子域>.<你的域名> @223.5.5.5     # 阿里,查国内可达性时用

# ③ 问你自己电脑的缓存
dscacheutil -q host -a name <子域>.<你的域名>    # macOS
```

### ⚠️ 一个能把人骗惨的本机坑

**症状:全世界都能打开,就你自己的电脑打不开。**

本项目 2026-08-23 实测撞到过:在 DNS 记录还没生效时查过一次,macOS 把"这个名字不存在"这个**否定结果也缓存了下来**。之后记录明明已经全球生效,本机 `curl` 还是 1 毫秒就返回失败——快得根本不像超时,而是本机直接从缓存里回了"没有这个域名"。

判断方法:`dig @1.1.1.1` 查得到,但本机 `curl` 立刻失败,就是它。

解药(macOS):

```bash
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
```

**养成习惯:在记录还没配好之前,别反复去 ping 那个域名**——每查一次都在给自己种一颗负缓存。

## 域名和备案(中国大陆相关)

如果你的网站要跑在**中国大陆境内的服务器**上,并且用域名访问,法规要求先完成 **ICP 备案**——由服务器提供商(阿里云、腾讯云等)代为提交,通常一到两周。

几条实用的:

- **备案跟的是"服务器在哪",不是"域名在哪买的"**。服务器在香港、新加坡、美国,都不需要备案
- 不是所有域名后缀都能备案,工信部有核准名录,冷门后缀可能不在里面——**买之前先查**
- 本项目的域名没有备案,所以内网穿透档选边缘节点时必须选境外地区。这条已经实测跑通:在 cpolar 后台把自定义域名保留在香港节点,未备案域名照常可用
