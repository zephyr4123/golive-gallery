# 04 · Git 与 GitHub

> 两个名字长得像,是两样东西:**Git 是装在你电脑上的工具,GitHub 是一个网站。**
> 这一篇讲清楚它们各自是什么,以及为什么在最省事的那条上线路径里,`git push` 就等于发布。

## Git 解决的是什么问题

没有版本控制的时候,人是这么保存进度的:

```
网站最终版.zip
网站最终版2.zip
网站最终版-真的最终.zip
网站最终版-改完客户又改回来了.zip
```

三个月后没人知道哪个是哪个,更没人知道"客户当时改了什么"。

**Git 是一台给文件夹用的时光机。** 你在关键节点告诉它"记一下现在这个状态",它就存一个快照。之后你可以:

- 看任意两个时刻之间**具体改了哪几行**
- 退回到任何一个历史时刻
- 开一条岔路做实验,搞砸了整条丢掉,主线毫发无伤

最后这条是本项目的工作方式:**做新东西先开分支,在分支上做完、验证过再合并主干**。有了这张保护网,才敢大刀阔斧地改。

## 五个词,够用了

### 仓库(repository / repo)

一个被 Git 管起来的文件夹。项目根目录下有个隐藏的 `.git/` 文件夹,所有历史都存在里面。删掉 `.git/`,就退化成一个普通文件夹,历史全没。

### 提交(commit)

一次快照,也是 Git 的基本单位。每个 commit 包含:改了哪些文件、改了哪几行、谁改的、什么时候、**以及一句说明为什么改**。

```bash
git status              # 现在有哪些改动还没记录
git add 文件名           # 挑出这次要记录的改动
git commit -m "说明"     # 记录下来
git log --oneline       # 看历史
```

那句说明不是走过场。**它是写给三个月后的人看的**——那个人大概率就是你自己,而且已经完全不记得当时为什么这么改。本项目的规矩是:说明写中文,讲清"改了什么、为什么改",技术名词(文件名、命令、API 名)保留英文。

还有一条:**小步快跑,一个逻辑单元一个 commit**,不要攒一个星期的改动堆成一个胖 commit。胖 commit 出了问题没法单独回退,等于白记。

### 分支(branch)

一条平行的时间线。默认那条通常叫 `main`。

```bash
git switch -c feat/新功能    # 开一条新分支并跳过去
git switch main             # 回到主干
git merge feat/新功能        # 把分支的成果并回主干
```

典型用法:主干永远保持能用的状态,所有新工作在分支上做,验证通过了才合并。本项目现在这些基础文档就写在一条叫 `feat/tunneling-tier` 的分支上。

### 远端(remote)

你电脑上的仓库是完整的,历史都在本地。**远端**是同一个仓库在别处的副本——通常在 GitHub 上,用来备份和协作。

```bash
git push     # 把本地的提交推到远端
git pull     # 把远端的更新拉到本地
```

🔴 **合并主干、push 到远端、改写历史之前,先确认。** 分支内部随做随提不用问任何人,一旦出了分支就要谨慎——这些操作会影响到别人。

### 忽略(.gitignore)

有些文件不该进版本库,列在项目根的 `.gitignore` 文件里,Git 就当没看见。

本项目忽略掉的:

| 忽略什么 | 为什么 |
|---|---|
| `node_modules/` | 几万个文件,能由 `package-lock.json` 完整重建([03 篇](03-node-and-npm.md)) |
| `dist/` | 构建产物,`npm run build` 随时重新生成 |
| `.env` | **装着密钥和私有配置** |
| `.playwright-mcp/` | 浏览器验证时的临时截图 |

## 一条不能踩的红线:密钥永远不进 Git

🔴 **API 密钥、令牌、密码、私钥,一个字节都不许提交进版本库。**

原因不是"别人会看到"这么简单——**Git 的核心特性就是什么都留着**。你今天提交了一个密钥,明天发现了,删掉文件再提交一次,那个密钥**仍然完整地躺在历史里**,任何人 clone 下来都能翻出来。

真要清干净,得用 `git filter-repo` 这类工具重写整个历史,然后强制推送覆盖远端——这会把所有协作者的本地副本搞乱。本项目就做过一次(2026-08,为了把域名从历史里洗掉),不是什么愉快的经历。

正确做法:

- 密钥放**环境变量**,或者放 `.env` 文件并且**先把 `.env` 写进 `.gitignore` 再创建它**
- 代码里只写变量名,不写值
- 提交前扫一眼 `git status`,确认没有意外文件被带上

顺带说本项目的另一条相关原则:仓库里所有实例私有的值(域名、主机名、项目名)一律配置注入。**这不是为了保密,是为了解耦**——任何人 fork 下来配上自己的值就能用。

## GitHub 是什么

GitHub 是一个**托管 Git 仓库的网站**。它不是 Git,Git 离了它照样能用(本地仓库完全独立)。

它提供的是 Git 本身没有的东西:

- **一个所有人都能访问的仓库副本**——协作与备份
- **Issue** —— 记录任务、bug、决策的地方
- **Pull Request** —— 提议把某个分支合并进主干,并且在合并前评审
- **Actions** —— 你 push 之后,自动跑测试、跑构建、跑部署
- **Pages** —— **直接把仓库变成一个网站**

同类的还有 GitLab、Gitee、Bitbucket,机制一样,换个网站而已。

## 为什么 `git push` 就能让网站上线

这是最省事的那条上线路径([01 · 免费托管](../guide/01-free-hosting/README.md))的核心机制。

GitHub Pages / Cloudflare Pages 这类平台,做的事情是:**盯着你仓库的某个分支,你一 push,它就自己拉代码、自己构建、自己把产物发布出去。**

整条链子:

```
你 git push
   ↓
平台收到通知,拉走最新代码
   ↓
平台在自己的机器上跑 npm ci && npm run build
   ↓
把构建出的 dist/ 部署到它的 CDN
   ↓
访客访问你的域名 → 拿到新版本
```

从你按回车到线上更新,通常一两分钟。**你不需要有服务器,也不需要懂部署**——平台把中间全包了。

这也解释了为什么这条路对静态站几乎是白送的:平台只是在替你存文件、递文件,成本极低(见 [01 篇](01-how-the-web-works.md)静态站与动态站的区别)。

两个直接后果,提前知道能少踩坑:

- **平台是在它自己的机器上构建的**,不是用你电脑上的 `dist/`。所以你本机构建成功不代表平台一定成功——Node 版本、依赖、环境变量都可能不同。本项目给 Acreage 站在仓库里钉死了 Node 版本,就是为了消掉这个变量
- **平台只能拿到你提交上去的东西**。被 `.gitignore` 挡住的文件它看不见。所以真正需要它知道的配置(比如环境变量),要在平台面板里单独填

## 记录也是资产

最后一条是工作方式,不是技术:

**凡事沉淀成 issue。** 任务、bug、想法、决策,随做随记。原因很实在——写下来的上下文才是以后用得上的上下文。三个月后你问"当初为什么选 Cloudflare 不选 Vercel",只有两个地方能回答你:commit 记录,和 issue 记录。

本项目就是这么做的:每条重要决策都有出处,`git log` 是排查问题时的第一手依据。
