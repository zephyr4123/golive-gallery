# 08 · 内网穿透的原理

> 网站在你电脑上跑得好好的,`http://localhost:4173` 一打开就是。
> 你把这个地址发给朋友,他打不开——他打开的是**他自己**的电脑。
>
> 这一篇讲清楚:为什么你家那台机器公网找不到,以及隧道是怎么绕过去的。
> 具体用哪家、怎么配,在 [02 · 内网穿透](../guide/02-tunneling/README.md)。

## 为什么公网找不到你的电脑

### 你的电脑没有公网地址

打开电脑的网络设置,看到的 IP 多半长这样:`192.168.1.7`、`10.0.0.5`、`172.20.10.3`。

这三类地址是**私有地址**,全世界的家庭和办公室都在重复使用。你家路由器下的 `192.168.1.7`,和隔壁家的 `192.168.1.7` 是两台完全不同的电脑。

**私有地址在公网上没有意义**,没人能靠它找到你。整栋楼、甚至整个小区,对外可能只共用一个公网 IP。

### NAT:一扇只能从里往外开的门

把私有地址翻译成公网地址的那个东西叫 **NAT**(Network Address Translation),就跑在你家路由器上。

它的工作方式是**记账**:

```
你打开某网站 ──> 路由器记一笔:"内网 192.168.1.7 的 51234 端口,
                              问了 1.2.3.4 的 443 端口"
                 ──> 用公网 IP 发出去
对方回包    ──> 路由器查账本:"哦,这是给 192.168.1.7 的" ──> 转进去
```

关键在于:**这本账只在你主动发起时才会记上一笔。**

外面有人想主动连你,路由器一查账本——没有这一笔——不知道该转给内网哪台机器,直接丢弃。

**这就是全部原因。** 不是防火墙特意拦你,是根本没有信息决定该转给谁。这个设计顺带成了一层免费的安全防护:你家所有设备默认不对公网暴露。

### 传统解法为什么普通人走不通

理论上有办法让外面能主动连进来,但每条都有拦路虎:

**端口映射(port forwarding)** —— 在路由器上手工加一条规则:"凡是打到公网 IP 的 4173 端口的,转给内网的 192.168.1.7:4173"。技术上可行,但:

- 要能进路由器管理后台(公司/学校/合租房通常进不去)
- 你的公网 IP 大概率是**动态的**,重启光猫就变
- 🔴 **相当于在你家网络上开了一个对全世界敞开的口子**,后面直接是你的电脑

**运营商级 NAT(CGNAT)** —— 更麻烦的是,现在很多宽带**根本不给你公网 IP**,你家路由器拿到的也是运营商内网的地址。这种情况下端口映射做了也没用,因为你压根没有一个"公网 IP"可以被打到。

判断你有没有公网 IP:

```bash
curl -s https://ifconfig.me      # 公网看到的你
```

把这个结果和路由器 WAN 口显示的 IP 比一比。**不一样,就说明你在运营商大网 NAT 后面**,端口映射这条路直接封死。

## 隧道:反过来,由你主动打出去

既然 NAT 只允许从里往外发起连接,那就**顺着它的规则来**。

你在自己电脑上跑一个客户端程序,它**主动**连上服务商在公网的服务器,并且**保持这条连接不断开**:

```
         你的电脑                              公网
    ┌──────────────┐                    ┌──────────────┐
    │ 网站跑在      │                    │  服务商的     │
    │ localhost:4173│                   │  边缘节点     │
    │              │                    │              │
    │ 隧道客户端 ───┼──主动发起,长期保持──>│  (有公网地址) │
    └──────────────┘                    └──────┬───────┘
                                               │
                                          访客访问这里
```

这条连接是**你发起的**,所以 NAT 的账本上有它,路由器乐意维持。

之后事情就反过来用了:

1. 访客访问服务商给你的那个公网地址
2. 服务商收到请求,**顺着那条早就建好的连接**把请求塞回你的电脑
3. 你机器上的客户端把请求转给 `localhost:4173`
4. 网站生成响应,原路返回

**没有任何人"主动连"你的电脑。** 数据是在一条你自己打出去的连接里双向跑的。

所以这一档的全部性质,好的坏的,都由这一条推出来:

- ✅ 不需要公网 IP
- ✅ 不需要进路由器改设置
- ✅ 不需要在防火墙上开口子——**没有新的入口暴露给公网**,只有一条你主动维持的出站连接
- 🔴 **那条连接断了,一切结束**

## 一条请求实际经过三跳

排查的时候这个模型比什么都有用——**三跳各有各的失败长相**:

```
访客 ──①──> 服务商边缘节点 ──②──> 隧道客户端 ──③──> localhost:4173
```

| 断在哪 | 访客看到什么 | 说明 |
|---|---|---|
| ① 之前 | 域名解析失败 | DNS 问题,和隧道无关([05 篇](05-domain-and-dns.md)) |
| ① | 服务商的错误页(如 Cloudflare `530`) | **隧道进程没了**——你关机/关终端就是这一幕 |
| ② | `502 Bad Gateway` | 隧道活着,但客户端连不上本地服务 |
| ③ | `403` 之类的应用层错误 | 全链路是通的,是本地服务自己拒绝了 |

**看到 502 别去查 DNS,看到解析失败别去重启隧道。** 状态码是哪一层发的,直接指出了该修哪一跳。

## 隧道和托管的本质区别

| | 托管平台 | 隧道 |
|---|---|---|
| 文件在哪 | 复制到平台的服务器上 | **只在你的电脑上** |
| 你关机之后 | 照常访问 | **立刻打不开** |
| 上线要做什么 | `git push`,然后就没你事了 | 保持本机和进程活着 |
| 改了代码 | 要重新 push、等平台构建 | 本地重新构建,**刷新就是新的** |
| 适合什么 | 长期在线的正式站点 | 临时给人看、边改边看 |

最后一行才是重点。这两样东西**不是同一件事的两种做法**,而是两件不同的事。

## 「关掉就没」不是缺陷

这一档最容易被误读成"一种更省钱的托管",然后得出"限制真多"的结论。

换个角度就全通了:**很多时候你要的根本不是一个 7×24 的服务。**

- 刚做完一个页面,想让朋友现在打开看一眼,听听他什么感觉
- 把链接发给客户验收,他点完就完了
- 让设计师在**他自己的手机上**真机点一遍,而不是看你的截图
- 边改边给对方看,改一行刷新一次,不用等任何构建

这些场景本来就是**临时的**。没有人指望它半夜还开着,也没有人会因为它明天打不开而报 bug。

对刚入门的人来说,这条路还有一个别的路给不了的好处:**它是"让别人看到我做的东西"这件事最短的一条路径。** 不用买域名、不用注册托管平台、不用懂部署,装一个客户端、敲一条命令,链接就有了。先体验到"有人打开了我做的页面"这件事本身,再去学后面那些,动力完全不一样。

所以本项目的做法是:**不追求常驻,而是把状态标清楚,按需开着。** 站点在机器上标了 `availability: best-effort`,画廊的"已上线站点"表里不收它、也不挂假的常驻链接——打不开是这条路的结构性性质,把它讲清楚就是教学内容,拿它去糊一个撑不住的链接才是骗人。

这层"它其实是开发流程里的 stage 环境"的完整展开,在 [02 档正文](../guide/02-tunneling/README.md#它不是托管是-stage-环境)。

## 安全:多了一件要自己负责的事

隧道做的事情是"把你本机的一个端口暴露到公网",风险面和托管完全不同:

- **只暴露该暴露的那一个端口**,别图省事映射整个网段
- **本机不是服务器**。那个端口后面的进程有你用户的全部权限,同一台机器上还有你的代码、密钥、浏览器数据。伺服的必须是构建产物目录(`dist/`),不是项目根
- 🔴 **公开分享一律用 `vite preview`,绝不用 `vite dev`**——开发服务器会把源码和项目结构一起暴露出去([03 篇](03-node-and-npm.md))
- **地址会被扫**。隧道服务商的域名段是公开的,这些年被大量用于钓鱼,导致部分企业网关会**整域拦截**。你把链接发给同事他打不开,原因可能是对方公司的安全设备,不是你配错了
