# 00 · 基础:四个心智模型

> 这一章只讲本项目上线第一个站真正用到的四个概念。每个模型配一条自查命令——概念记不住没关系,命令能跑出真相。

## 模型一:域名 = 一条登记记录,注册商 ≠ 解析商

买域名买到的不是一台服务器,而是在**注册局**(比如 .art 的注册局)登记的一条记录:"这个名字归你,并且由某几台 DNS 服务器负责解析它"。

两个角色经常被混为一谈,其实完全可以分开:

- **注册商**(registrar):你在哪买的域名、在哪续费——本项目在腾讯云
- **DNS 托管商**(解析商):谁来回答"这个域名指向哪"——本项目在 Cloudflare

买域名时注册商默认把解析也包了(腾讯云配 DNSPod),但你随时可以只换解析商、不动注册商——这正是我们做的事(原因见 [Cloudflare 解析篇](../01-free-hosting/custom-domain-cloudflare.md))。

```bash
whois <你的域名> | grep -iE 'registrar|name server'   # 注册商与解析商,一条命令看清两个角色
```

## 模型二:DNS 记录,以及"CNAME 只能指域名"

解析商手里是一张表,每行一条记录。本项目只用到两种:

| 类型 | 含义 | 例 |
|---|---|---|
| A | 这个名字 → 这个 IP | `@ → 185.199.108.153` |
| CNAME | 这个名字 → 另一个名字(别名) | `dreamcore → <用户名>.github.io` |

**CNAME 的记录值只能是域名,不能带路径**。不存在 `xxx.github.io/仓库名` 这种记录——DNS 层只认识名字,不认识 URL。那平台怎么知道该回哪个站?靠 HTTP 请求里的 Host 头:流量到达平台后,平台查"哪个站登记了这个域名",按名字分发。所以同一个用户的一百个项目站,CNAME 记录值全都一样,互不打架。

```bash
dig +short CNAME dreamcore.<你的域名>    # 看别名指向
dig +short dreamcore.<你的域名>          # 看最终解析结果
```

## 模型三:NS 记录 = "这个域名归谁解析"

注册局层面记着一条 NS(Name Server)记录:这个域名的一切解析问题,去问这几台服务器。**换解析商 = 改这条 NS 记录**,操作入口在**注册商的域名管理页**(不在解析记录页——两者的区别是"由谁解析" vs "解析成什么")。

查询是一条链,每一环都可能有缓存:

```bash
dig +short NS art. | head -1                       # ① 找到顶级域的权威服务器
dig +short NS <你的域名> @a.nic.art                 # ② 问注册局:这个域名归谁解析(最权威,无缓存)
dig +short NS <你的域名> @8.8.8.8                   # ③ 问公共解析器(有缓存,可能滞后)
```

②和③不一致时,说明 NS 变更已在注册局生效、公共缓存还没过期——**这不是故障,是时间问题**(详见解析篇的缓存心法)。

## 模型四:HTTPS 证书跟着域名走,不跟服务器走

证书本质是"某个域名归你"的证明,里面写的是域名,和跑在哪台机器无关:

- 一台服务器可以挂无数张证书(TLS 握手时浏览器先报域名,服务器按名递证书,即 SNI)
- 一张证书可以部署在全球无数节点(CDN 的日常)
- **托管平台代管证书**:GitHub Pages、Cloudflare 都会替你向 CA(如 Let's Encrypt)自动申请、部署、续期,全程免费零操作

本项目的形态:Cloudflare 在边缘持有 `<你的域名>` 的证书并终结 TLS(访客看到的锁来自这里),CF 到源站再走另一段连接。

```bash
curl -sIv https://dreamcore.<你的域名>/ 2>&1 | grep -iE 'subject:|issuer:'   # 看证书签给谁、谁签的
```
